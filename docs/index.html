Refresh Opportunity Scoring: A Ranking Approach to Content Review Prioritization

Haris Bin Habib — FlyRank ML Internship, Applied Search Intelligence Track

Abstract. Content editors face a large inventory of pages and limited time to review them. This project asks which pages an editor should review first, given evidence of decline, using only signals observable before the decision point. I built a transparent rule-based baseline and compared it against two trained classifiers on FlyRank's pseudonymized search performance warehouse, using a client-grouped, time-aware validation design to avoid leakage. Against a base rate of 0.533, the baseline reached precision@50 of 0.640; logistic regression reached 0.680, a modest improvement, while a random forest reached only 0.560 despite having the highest overall ROC-AUC (0.615) of the three methods. The result is a ranked, reason-coded action queue — decision support for editorial review, not a causal claim about what fixes a page — and a reminder that a model's overall ranking quality and its precision at the very top of a list are not the same thing.

Introduction

FlyRank's content inventory spans hundreds of thousands of pages per client, far more than any editorial team can review individually. The decision this work supports is simple to state and hard to automate well: which pages should an editor look at first? A wrong answer costs either wasted review time (a false positive) or a missed decline that compounds before anyone notices (a false negative). Because editor capacity is fixed, the right metric is not overall accuracy but precision at the top of a ranked list — precision@K — matching how the output is actually consumed.

Data

This project uses the FlyRank internship warehouse release (build flyrank_pseudonymized_warehouse_release_v20260703), hosted on Hugging Face at FlyRank/internship-warehouse, specifically the dim_clients, dim_content, and fact_content_daily_performance tables. The daily fact table spans 2025-01-27 through 2026-06-30. I anchored my analysis at 2026-03-31 — a mid-panel date, chosen specifically to avoid the release's sealed final month, which is the natural outcome window for any past-to-future label. All identifiers (client and content IDs) are pseudonymized; no raw client names, domains, URLs, or query text are present in this release or in this paper.

Excluded by design: FlyRank's own product decision fields (health_score, priority_score, action_type) are not present in this release — my model only ever sees observable signals, never the product's own prior decisions.

The feature-and-label pipeline produced 120,258 (client, content) pairs with at least 100 impressions in the prior 90-day window. Of the 11,583 held-out test rows, 6,858 (59%) still showed activity within the last 30 days of that window; the remaining rows — pages already silent for 30+ days — were excluded from evaluation for reasons explained in Methodology.

Methodology

Unit of analysis: one (client, content) pair, aggregated over a rolling 90-day feature window ending at the decision point (2026-03-31).
Label: declined_next30 — impressions in the 30 days after the decision point falling below 70% of the prior-90-day impressions. This is a future-observed outcome, not a same-window proxy.
Features: prior-90-day impressions, clicks, average position, CTR, and days since last seen — all knowable strictly before the decision point.
Validation: a client-grouped train/test split (75/25), so no client's pages appear in both sets — preventing the model from memorizing client-specific patterns instead of learning generalizable signal.
Baseline: a transparent rule — flag a page as an opportunity if its prior-90-day impressions were at or above 500, scored by impression volume. No fitted weights.

An earlier version of this baseline flagged pages by a "days since last seen" staleness rule and reached a suspicious precision@50 of 1.000. Inspection showed every top-ranked page under that rule had already gone completely silent (zero impressions) for 30+ consecutive days before the decision point — predicting that an already-dead page stays dead is not a meaningful decline prediction, just a restatement of the same fact. I corrected this by restricting evaluation to pages that still showed some activity in the final 30 days of the feature window, where the outcome is genuinely uncertain, and redefined the baseline around impression volume instead. This is reported here in the interest of honest methodology.

The transparent baseline already outperforms random selection by a wide margin (0.640 vs. 0.533), meaning impression volume alone is a real, useful signal for this task. Logistic regression edges out the baseline (0.680), a real but modest 6-percentage-point gain — not the kind of dramatic improvement that would justify replacing a simple, explainable rule on its own. More strikingly, the random forest — despite having the best overall ROC-AUC of the three methods (0.615) — actually scores below the baseline on precision@50 (0.560). This is a useful reminder that a model can rank the full population better on average while still being worse at the specific task an editor cares about: getting the very top of a limited-capacity list right. With only five engineered features and a single time-anchored evaluation, this result should be read as an early, honest signal rather than a settled comparison — a natural next step would be testing whether additional features or a different decision threshold change which method wins at the top of the list.

Limitations & Honest Framing

  • This is a single time-anchored evaluation (2026-03-31); it has not yet been validated across multiple decision points or seasons, so these precision numbers may not hold at a different point in the year.
  • Client tracking history is uneven — some clients contribute thinner feature windows than others, which the model cannot distinguish from genuinely low activity.
  • The label is a threshold-based proxy for decline (impressions falling below 70% of the prior window), not a ground-truth business outcome.
  • Only five features were used (impressions, clicks, position, CTR, and days since last seen). The random forest's underperformance at precision@50 relative to the baseline may partly reflect this small feature set rather than a fundamental limit of the method.
  • This work never claims that a refresh causes recovery — that would require a controlled experiment. The output is decision support: a ranked, reason-coded starting point for human review, not a guarantee.
  • No claims are made about Google's ranking algorithm or AI search visibility.

Ranked Recommendations

The ranked queue (see work/outputs/capstone_ranked_queue.csv in the repo, 6,858 rows) is ordered by the logistic regression model's estimated decline probability — the method that won on precision@50, the metric that matches how a limited-capacity review queue is actually used. Each row carries a reason code and a suggested action (refresh). Several top-ranked pages carry substantial impression volume (70,000–180,000 in the prior 90 days), meaning even a modest false-positive rate among them still represents meaningful review time. An editor working from this list should sanity-check each recommendation against context the model cannot see — e.g. whether a nearby sibling page absorbed the traffic (consolidation) rather than a genuine decline.
